## Backend and upstream audit

The local DiagGen checkout remains at official commit `3d2d3779613b9253109f63e1ff345b11c9097b70`. The saved CPU checkpoint audit for the actual OmniPart mesh decoder found six sparse-convolution weights in the pretrained checkpoint that do not directly match TorchSparse's `kernel` parameters. The local official wrapper has no conversion, while `from_pretrained` loads with `strict=False`; a direct backend switch would leave those target kernels initialized and is not a valid repair. A compatible mapping and full-size output validation are still absent. The previously recorded per-member decoder comparison failed its feature tolerance, so it was not repeated.

The active OmniPart source still offers the `spconv` and `torchsparse` backends, and its app selects `SPCONV_ALGO=native`; the current run's saved log also records `ConvAlgo.Native`, so switching to that algorithm is already disproven for this failure. The upstream [spconv issue #604](https://github.com/traveller59/spconv/issues/604) remains open, and the [2.3.8 changelog](https://github.com/traveller59/spconv/blob/master/CHANGELOG.md) documents no fix for this size assertion. The [OmniPart backend wrapper](https://github.com/HKU-MMLab/OmniPart/blob/main/modules/part_synthesis/modules/sparse/conv/conv_torchsparse.py), [pretrained loader](https://github.com/HKU-MMLab/OmniPart/blob/main/modules/part_synthesis/models/__init__.py), and [TorchSparse Conv3d parameters](https://raw.githubusercontent.com/mit-han-lab/torchsparse/master/torchsparse/nn/modules/conv.py) were checked against the local source.
