# DiagGen incident 20261022_235219_ff1b8ecd0a10

## Finding

The capybara run stopped in the native `omnipart_generate_parts` stage. This is a sparse-kernel dependency limit, not a scheduler failure, a Genesis business halt, or a GPU memory-gate failure.

The durable stage record and stderr identify an fp16 spconv GEMM assertion. Its feature tensor had 6,874,752 rows and 192 channels, requiring 2,639,904,768 bytes for the checked input, above the kernel's signed-int32 ceiling of 2,147,483,647 bytes. The recorded GPU gate had passed with 65,296 MiB free against a 49,152 MiB minimum. The stage halted before producing its ten required outputs; no diagnostic episode or terminal recommendation was created.

## Official backend and checkpoint audit

The local official OmniPart source exposes `spconv` and `torchsparse` backends. The installed generation environment has PyTorch 2.7.0+cu128, spconv-cu126 2.3.8 and cumm-cu126 0.7.11; TorchSparse is not installed.

The cached official OmniPart model snapshot used for the audit is `dfc4b4c73e3f8c1bb6c8dd560373509f82010ab6`. Its mesh decoder config is resolution 64, 768 model channels, 8 latent channels, 12 blocks and fp16. The 181,903,412-byte checkpoint contains 120 tensors, including six sparse-convolution weight tensors named `*.conv.weight` with spconv layout `[out, kx, ky, kz, in]`.

OmniPart's TorchSparse wrapper constructs `torchsparse.nn.Conv3d` under `*.conv`; the official TorchSparse module stores its parameter as `kernel` with shape `[kernel_volume, in, out]`. OmniPart's `from_pretrained` loader calls `load_state_dict(..., strict=False)` and contains no backend-specific key or layout conversion. A direct backend switch would leave these six convolution kernels unmatched (and silently retain initialized parameters); it is not a valid repair. No backend switch, package install, source edit, precision change, or resolution change was made.

The official [spconv issue #706](https://github.com/traveller59/spconv/issues/706) remains open with the same int32-range assertion. The official [spconv changelog](https://github.com/traveller59/spconv/blob/master/CHANGELOG.md) does not document a 2.3.8 fix for this GEMM limit. The community workarounds in the issue do not establish numeric correctness for this workload. Previously recorded native-algorithm and per-member-decoding experiments were not repeated; the latter already failed its feature-tolerance comparison.
